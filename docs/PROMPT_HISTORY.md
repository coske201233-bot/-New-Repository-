> **プロンプト例 2-2**:

### Phase 4: データ整合性の担保・UUID移行・ゴーストデータ撲滅 (2026年5月下旬〜6月中旬)

#### ■ ユーザープロンプト / 課題要請
> **プロンプト例 4-1**:  
> 「カレンダーでシフトを削除したはずなのに、リロードするとゾンビのように復活してしまいます。ローカルストレージとSupabaseデータベースの間でデータ不整合が起きないよう完全に修正してください。」
> 
> **プロンプト例 4-2**:  
> 「データベースのID型でエラー（UUID型とTEXT型の不一致）が出て保存や削除に失敗することがあります。IDのスキーマを標準のUUIDに統一してください。」
> 
> **プロンプト例 4-3**:  
> 「以前のテストデータ（特定の時間休レコード等）が集計やカレンダーに残ってしまっているので、これを確実にパージ・除外してください。」

#### ■ 技術的実装対応・主要コミット
- `b09c891` / `b58b3a4` : ゾンビデータ復活バグの修正、カレンダー表示とサマリー集計の整合性100%統一。
- `9b2abbd` : 過去のゴースト時間休データを集計・レンダリングから除外する防護ロジック実装。
- `067f5a3` 〜 `af5bd73` : SQLの `id::text` キャスト混在を全廃し、ネイティブ `.in()` フィルタおよび標準 `crypto.randomUUID` に統一。
- `0588ec2` / `7aa8029` : 職員画面の無限ローディング解消、ログイン直後の残骸チラつきのアニメーション制御による撲滅。

## 3. まとめ・開発知見
シフトマネジャーの開発プロセスでは、**「現場の複雑な勤怠ルールへの適応」**と**「モバイル・Web両対応の堅牢なUI/データ同期」**の両立が継続的に追求されました。
特に、以下の技術的プラクティスが確立されています：
1. **厳密な時間管理**: 0.25時間刻みの時間休や、7.75h/7.5hの異動・雇用形態差の吸収。
2. **手動設定の絶対保護**: 自動シフト生成エンジンが管理者の手動確定データを上書きしない排他制御。
3. **多層防御の耐障害性**: ネットワーク切断時のローカルキャッシュ、ゴーストデータのサニタイズ、ホワイトスクリーントラップ。
4. **監査性の確保**: シフトの直接編集や承認・却下の全履歴をDBに永続化し、トラブルを未然に防止。
